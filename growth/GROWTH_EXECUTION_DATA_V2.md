# Beyond Growth — Execution Data v2

Status: **implemented / source-agnostic ingest ready / no club execution source connected yet**

## Why v2 exists

Growth Measurement v1 could store arm-level `exposed / purchasers / tickets / revenue / refunds / campaign cost`, but it used `exposed` as the denominator for uplift.

That is not the correct default for a randomized holdout. A person assigned to the holdout can still buy organically even though holdout exposure to the tested campaign is zero. Conditioning the comparison on actual exposure can introduce post-randomization bias.

Growth v2 therefore uses **intent-to-treat (ITT)**:

`assigned Treatment vs assigned Holdout`

`exposed` remains an execution-quality metric, not the causal denominator.

## Product flow

`Demand signal → Growth recommendation → Experiment → Assignment → Execution → Outcome data → ITT uplift → Incremental tickets → Incremental contribution → ROI`

Beyond still does **not** launch a campaign or change ticket prices automatically.

## Two supported assignment modes

### 1. `exact_manifest` — preferred

The execution source sends one pseudonymous assignment row per subject:

- `subjectKeyHash`
- `armKey = treatment | holdout`
- `assignedAt`
- optional source record key / non-PII metadata

The subject key must be a 64-character lowercase cryptographic hash. The preferred implementation is an **HMAC-SHA-256 generated upstream with a club-owned secret**. Do not send the email, phone number, name, raw customer ID, or raw user ID to Beyond.

Beyond stores exact assignment rows in the non-exposed `private` schema. The dashboard only sees counts/statuses.

Guardrails:

- the same pseudonymous subject cannot move from Treatment to Holdout or vice versa;
- `assignedCount` in metrics must equal the exact manifest count;
- duplicate assignment rows are idempotent;
- raw PII fields are rejected by the Edge ingest function.

### 2. `aggregate_only`

For a club/source that cannot send the exact manifest, Beyond accepts arm-level cumulative aggregates only.

This still supports ITT if the source supplies the true assigned populations, but the assignment is less auditable because Beyond cannot independently deduplicate the members of each arm.

The dashboard labels this mode explicitly as `Aggregate only`.

## Protected ingest endpoint

Supabase Edge Function:

`growth_execution_ingest_v1`

Security:

- `verify_jwt = true`;
- the function additionally requires the project service-role bearer token;
- it is intended for a trusted backend/automation adapter, never the public browser;
- service-role credentials must never be exposed to a club user or frontend bundle.

The function:

1. accepts `POST` only;
2. caps payload size and assignment rows;
3. rejects known raw-PII keys;
4. normalizes and validates the payload shape;
5. canonicalizes the JSON and generates `payloadSha256`;
6. sends the transaction to `ingest_growth_execution_batch_v2`;
7. returns the accepted/duplicate result.

## Metric semantics

All arm metrics are **cumulative as of `observedAt`**.

| Field | Meaning |
| --- | --- |
| `assignedCount` | Population randomized/assigned to the arm. Primary ITT denominator. |
| `exposedCount` | Assigned population actually delivered/exposed to the tested intervention. |
| `purchasersCount` | Purchasers in the assigned arm, including organic holdout purchasers. |
| `ticketsCount` | Tickets purchased by the assigned arm. |
| `grossTicketRevenue` | Gross ticket revenue generated by the assigned arm. |
| `refundsAmount` | Cumulative refunded ticket revenue. |
| `campaignCost` | Direct cumulative campaign cost allocated to the arm. |

The ingest rejects cumulative regressions: assigned, exposed, purchasers, tickets, gross revenue, refunds, campaign cost and observation time cannot move backwards.

## ITT calculations

### Conversion rate

`purchasers / assigned`

### Ticket rate

`tickets / assigned`

### Incremental tickets on Treatment population

`(Treatment ticket rate - Holdout ticket rate) × Treatment assigned`

### Gross revenue per assigned

`gross ticket revenue / assigned`

### Incremental gross revenue

`(Treatment gross revenue per assigned - Holdout gross revenue per assigned) × Treatment assigned`

### Net revenue per assigned

`(gross ticket revenue - refunds) / assigned`

### Incremental net revenue

`(Treatment net revenue per assigned - Holdout net revenue per assigned) × Treatment assigned`

### Incremental campaign cost

`Treatment campaign cost - Holdout campaign cost scaled to Treatment assigned population`

### Incremental contribution

`incremental net revenue - incremental campaign cost`

### ROI

`incremental contribution / incremental campaign cost`

ROI is shown only when incremental campaign cost is positive.

## Reporting gate

`min_assigned_per_arm` defaults to **100**.

This is an operational gate, **not statistical significance**.

Dashboard measurement states:

- `draft_not_started`
- `awaiting_assignment`
- `assignment_mismatch`
- `awaiting_outcome_data`
- `collecting_sample`
- `descriptive_only`
- `experiment_observed`

Portfolio-level business totals only include `experiment_observed` and explicitly non-causal `descriptive_only` rows. Raw directional calculations from incomplete samples are not rolled into the headline business result.

## What the first club/source integration must provide

A minimal pilot source adapter needs only:

1. the experiment key;
2. the actual Treatment/Holdout assignment (exact pseudonymous manifest preferred, otherwise counts);
3. cumulative campaign exposure/delivery per arm;
4. purchasers and ticket count per arm;
5. gross ticket revenue and refunds per arm;
6. campaign cost per arm;
7. stable source and batch identifiers.

Once those values arrive, Beyond can calculate and display the real business result without another model/schema redesign.
